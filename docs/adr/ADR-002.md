# ADR-002: Phase 2 Recall Mode Engine and CI Security Mitigations

**Status**: Accepted  
**Date**: 2026-04-12  
**Project**: omoide — local encrypted secret manager  
**Author**: Inigo  

---

## Context

Following the completion of Phase 1 (Core Crypto Primitives and Vault Format), `omoide` is proceeding with Phase 2: the "Recall Mode" engine. The core philosophy of `omoide` relies on cognitive-cryptography-driven authentication, where the Master Password must be consistently rehearsed to prevent memory degradation, eliminating the risk of catastrophic forgetting while maintaining maximum security.

Additionally, during continuous integration (CI) tests, a security advisory error surfaced indicating that `rand` crate version `0.8` possessed unsound behavior. Given the threat model of the system, this vulnerability must be mitigated immediately alongside the feature updates.

---

## Decisions

### 1. Spaced Repetition System (SRS) Integration

**Decision**: Integrate an SRS state directly into the vault structure to enforce Master Password "Emergency Access Rehearsals." 

**Rationale**:
- **Vault Binding**: `SrsState` is now structurally bundled within the `VaultHeader`, tying the rehearsal schedule to the vault instance itself.
- **Algorithm Parameters**: The default interval is set at 12 hours. Successful unlocks multiply the interval by 1.5, while failures penalize by dividing it by 2.0. This exponential curve efficiently forces early practice and gently tapers off as cognitive memory hardens. 
- **Time Representation**: Rehearsal times use Unix timestamp seconds (`u64`) to minimize platform-specific parsing complexities. Interval and due date algorithms are isolated within `omoide-core/src/srs.rs`. 

### 2. Vault Schema Version Migration

**Decision**: Increment the `VAULT_VERSION` from `1` to `2`. 

**Rationale**: 
- The addition of `SrsState` in `VaultHeader` (`omoide-format`) modifies the underlying CBOR serialization layout.
- `omoide-env` reflects this change by updating the global `VAULT_VERSION` constant, acknowledging that legacy `v1` implementations are incompatible with the SRS framework without a dedicated migration step.

### 3. Master Password "Anchor Memory" Wizard

**Decision**: Introduce an interactive "Password Architect Wizard" natively into `omoide-cli`.

**Rationale**:
- Providing a standard CLI pathway to scaffold Master Passwords utilizing a "Nonsense Logic" mnemonic PAO schema (Place + Action + Object, e.g., `AtticSprintingViolin`) directly improves user experience to the strict recall requirements of the SRS. 

### 4. Upgrade `rand` Dependency

**Decision**: Upgrade the `rand` crate workspace dependency from `0.8` to `0.10.0-rc.9`.

**Rationale**:
- A CI security job uncovered an unsoundness vulnerability in the `0.8` version. Upgrading to the `0.10.0-rc.9` release candidate immediately mitigates the vulnerability within the `omoide` threat model, allowing security pipelines to pass.

### 5. Migrate from `OsRng` to `SysRng`

**Decision**: Replace the invocation of `OsRng.fill_bytes()` with `SysRng.try_fill_bytes()` via the `TryRng` trait.

**Rationale**:
- Following the update to `rand 0.10`, the recommended OS randomness generator transitioned to `SysRng`. 
- During the implementation, attempting to conventionally use `.fill_bytes()` generated a compile-time error. This happened because in `rand 0.10`, `SysRng` does not implement the infallible `RngCore` trait, recognizing that OS entropy sources can fail.
- Instead, `SysRng` relies on the `TryRng` trait. Shifting to `try_fill_bytes` safely resolves the error by enforcing explicit OS failure control. In the event of system entropy exhaustion, the app unpacks the `Result` and prints a deterministic error string (`"CRITICAL: OS failed to provide secure randomness."`), matching modern Rust safety profiles.

---

## Consequences

- The vault file format is substantially modified to persist SRS intervals. Any subsequent features tracking further rehearsal metadata will necessitate a subsequent version format bump.
- The User Experience changes: users must now practice typing their Master Password on a schedule. If they fail or miss rehearsals, they will be forced to practice more often.
- CI pipeline blocking related to `cargo deny` dependency tracking has been resolved, asserting that primitive security generators remain structurally sound.

## Update 1: Phase 2 Closure (2026-05-02)

**Status**: Accepted  
**Author**: Inigo

### Context

Following full implementation of the Auth Orchestrator state machine (Task 13) and
a structured workspace review on May 1, 2026, a set of documentation contradictions
and code-quality items were identified and resolved before Phase 2 sign-off.

### Additional Decisions

#### A1. Resolve `PHASE_2_SCHEMA.md` Contradiction

**Decision**: Rewrite `docs/PHASE_2_SCHEMA.md` to formally supersede the original
per-entry `StrikeCounter` proposal and document the implemented plaintext-header
design.

**Rationale**: The original proposal stated SRS state *must not* be in the plaintext
header. The implementation correctly stores it there to allow pre-decryption reprompt
gating, but the document was never updated, which created a documentation liability.
The rewrite marks the original proposal as "Superseded", documents the implemented
`SrsState`-in-`VaultHeader` design, and formally records the trade-off as
**"Accepted Risk — Usage Pattern Side Channel"**: an attacker with read-only vault
access can observe rehearsal metadata but cannot learn entry content.

#### A2. Correct `CryptoError` Variant for Encryption Failures

**Decision**: Add `CryptoError::EncryptionFailed` to `omoide-crypto/src/error.rs`
and fix `aead.rs` to map `encrypt_in_place` failures to this variant instead of
the pre-existing `DecryptionFailed`.

**Rationale**: Mapping an encrypt failure to `DecryptionFailed` made it impossible
for callers to distinguish the error path. This is a semantic correctness fix with
no functional impact.

#### A3. Remove Unused `secrecy` Dependency

**Decision**: Remove `secrecy = "0.8"` from the workspace `Cargo.toml` and from
`omoide-crypto`, `omoide-core`, and `omoide-cli` crate manifests.

**Rationale**: `secrecy` was pulled in as a planned future dependency (for
`Secret<T>` / `[REDACTED]` debug masking) but was never imported in any `.rs`
file. Dead dependencies add compile time and binary size with no benefit.
`THREAT_MODEL.md` has been updated to note it as "planned, not yet active."

#### A4. Enforce `-D warnings` via `.cargo/config.toml`

**Decision**: Populate `.cargo/config.toml` with `rustflags = ["-D", "warnings"]`.

**Rationale**: Without this flag, compiler warnings can accumulate silently across
local and CI builds. Treating warnings as errors ensures the codebase stays clean
with no technical debt going unnoticed.

#### A5. Implement Real Fuzz Target for `decrypt_entry`

**Decision**: Replace the stub `fuzz_target_1.rs` with a real harness that exercises
`omoide_crypto::decrypt_entry` with arbitrary attacker-controlled inputs.
Add `omoide-env` as a path dependency to the fuzz crate so named size constants
(`AES_NONCE_SIZE`, `HEADER_AAD_SIZE`) are used instead of magic numbers.
Add `EntryKey::from_bytes` constructor to support construction from external crates.

**Rationale**: The fuzz target is the primary automated mechanism for catching
panics in the AEAD decryption path. The previous stub provided zero coverage. After
implementation, a 61-second run of 7.6 million iterations produced no panics,
covering 188 of 224 features. The fuzz corpus is excluded from version
control via `.gitignore`.

#### A6. Upgrade `rand` to Stable `0.10`

**Decision**: Change the workspace `rand` version specifier from `"0.10.0-rc.9"`
to `"0.10"`, resolving to stable `0.10.1`.

**Rationale**: `rand 0.10` reached stable release after ADR-002 was originally
written. Pinning to the RC was a temporary measure; the SemVer range `"0.10"`
now tracks stable patch releases automatically while keeping the `Cargo.lock`
reproducible.

#### A7. Add `--version` Flag to CLI

**Decision**: Add a `--version` / `-V` flag to `omoide-cli/src/main.rs` using
a manual `std::env::args()` check.

**Rationale**: A version flag is a baseline expectation for any CLI binary.
Implemented without adding a heavy argument-parsing dependency since the CLI
currently has no other argument-parsing needs.

#### A8. Correct Documentation Inaccuracies in README and THREAT\_MODEL

**Decision**: Update `README.md` and `docs/THREAT_MODEL.md` to reflect the
current state of the codebase.

**Rationale — README changes**:
- KDF parameters corrected to match `omoide-env` constants
  (`KDFPARAMS_MEM_COST = 65536` KiB = 64 MB, `KDFPARAMS_TIME_COST = 4`).
- Library name corrected from `ring` to `aes-gcm` (the actual crate used).
- Architecture caption stale reference to `omoide-store` removed
  (the crate is `omoide-format`).
- Recall Mode description updated: strike counter is now described as
  persisted in the plaintext vault header (metadata only), not as encrypted.
- Roadmap entry for "Recall Mode engine" updated from *In Progress* to
  *Completed*.

**Rationale**:
- Last Updated date advanced to May 2, 2026.
- `secrecy` crate reference updated to reflect it is planned but not yet
  active in the codebase (consistent with A3 above).

### Consequences

- All 41 workspace tests continue to pass with zero warnings under `-D warnings`.
- The fuzz harness is now a real security regression gate rather than a
  placeholder.
- Documentation (README, THREAT\_MODEL, PHASE\_2\_SCHEMA) is now consistent
  with the implemented codebase.
- Phase 2 is considered **completed**. Remaining work (per-entry SRS granularity,
  BIP39 recovery flow, desktop UI) is deferred to Phase 3.
