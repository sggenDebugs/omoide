# ADR-001: Vault Format and KDF Design Decisions

**Status**: Accepted  
**Date**: 2026-04-03  
**Project**: omoide — local encrypted secrets vault  
**Author**: Inigo  

---

## Context

`omoide` requires a vault file format and key derivation strategy that satisfies
the following constraints from the threat model:

- **T1** — Secret material must never be paged to swap and must be zeroed after use
- **T2** — Vault file must be resistant to offline GPU brute-force attacks
- **T3** — BIP39 recovery seed wrapping key must be cryptographically independent
  from all vault entry encryption keys
- **T5** — Dependencies must be auditable

The decisions recorded here are **frozen at vault creation time**. Changing KDF
parameters after vault creation requires a migration tool. Do not alter these
defaults without re-running `omoide bench-kdf`, updating this ADR, and
incrementing the vault format version.

---

## Decisions

### 1. AEAD Algorithm: AES-256-GCM

**Decision**: Use AES-256-GCM via the `aes-gcm` RustCrypto crate.

**Rationale**:
- Target platform is x86-64 desktop only. AES-NI is present on all supported
  hardware, making AES-256-GCM faster than ChaCha20-Poly1305 in software.
- Aligns with TLS 1.3 and
  disk encryption ecosystem expectations.
- Nonce-reuse catastrophic failure mode is mitigated by per-entry HKDF subkeys
  (no key is ever reused).

---

### 2. KDF Algorithm: Argon2id

**Decision**: Use Argon2id via the `argon2` RustCrypto crate (`std` feature enabled).

**Rationale**:
- Winner of the Password Hashing Competition (PHC). Memory-hard and
  side-channel resistant (hybrid of Argon2i and Argon2d).
- OWASP-recommended for password storage as of 2024.
- No fallback to PBKDF2 or bcrypt — both are insufficiently memory-hard for
  modern GPU attacks.

---

#### Analysis

Based on comprehensive benchmarking across 7 test runs on the development machine (4-core, 8GB RAM, 256GB storage), the configuration **`m=65536, t=4, p=1`** (64 MB memory, 4 iterations, 1 parallelism) has been selected as the production Argon2id parameter set.

**Benchmark Summary for `m=65536 t=4 p=1`:**

| Metric | Value |
|--------|-------|
| Average execution time | ~325 ms |
| Observed range | 313.5 ms – 337.8 ms |
| Variability (spread) | ~7.6% |
| Deviation from 300 ms target | +8.3% |

**Rationale for Selection:**

1. **Consistent Performance**: With only ~7.6% variability across runs, this configuration delivers predictable login latency—critical for user experience and avoiding timeout-related failures.

2. **Proximity to Target**: Averaging ~325 ms stays within an acceptable margin of the 300 ms design target while providing headroom for minor system load fluctuations.

3. **Enhanced Security Posture**: The 64 MB memory setting significantly raises the cost of GPU/ASIC brute-force attacks compared to the OWASP baseline (`m=19456` ≈ 19 MB). Argon2id's memory-hardness makes this the most effective lever for increasing attack cost.

4. **Hardware Compatibility**: On the target hardware profile (8 GB RAM), 64 MB represents <1% of system memory, leaving ample headroom for concurrent operations. The single-threaded parallelism (`p=1`) prevents login attempts from saturating all 4 cores, mitigating denial-of-service risk.

5. **Future-Proofing**: This configuration balances current hardware constraints with security longevity. Should deployment targets shift to significantly weaker hardware, parameters can be re-evaluated via the same benchmarking methodology.

**Decision**:
- Adopt `m=65536, t=4, p=1` as the main Argon2id parameters for the vault KDF.
- Re-evaluate if target hardware profile changes or if login latency monitoring indicates user experience issues in production.

#### Why `p=1`

Parallelism is set to 1 (single-threaded unlock path). Rationale:
- `omoide` targets interactive desktop use — a single unlock operation per
  session, not batch processing.
- `p=1` avoids consuming multiple CPU cores during vault unlock, which would
  be noticeable on low-end hardware.
- The memory-hardness guarantee (`m=65536`, 64 MiB) provides the primary
  brute-force resistance, not parallelism. An attacker with `p>1` hardware
  gains no advantage because the bottleneck is memory bandwidth, not
  thread count.

### 4. Subkey Derivation: HKDF-SHA256

**Decision**: Derive per-entry 32-byte encryption keys from `MasterKey` using
HKDF-SHA256 (`hkdf` RustCrypto crate). `MasterKey` never directly encrypts data.

**Rationale** (RFC 5869 compliant):
- `MasterKey` is Argon2id output — uniformly distributed, high entropy,
  qualifies as IKM for HKDF.
- Per-entry HKDF subkeys provide **key separation**: compromising one entry key
  reveals nothing about other entry keys.
- The `entry_id` (UUID bytes, 16 bytes) is used as the HKDF salt, making each
  entry's key unique even under the same master key.
- The `info` tag separates key purposes:

| info tag | Purpose |
|---|---|
| `b"entry-enc"` | Vault entry encryption key |
| `b"seed-wrap"` | BIP39 recovery seed wrapping key (reserved, future sprint) |

**T3 mitigation**: `b"seed-wrap"` and `b"entry-enc"` produce cryptographically
independent keys even if the same `entry_id` is used. This is verified by the
test `entry_enc_and_seed_wrap_tags_produce_different_keys`.

**Why `Hkdf::new` over `Hkdf::from_prk`**: `from_prk` does not accept a salt
parameter — switching to it would silently drop `entry_id` from the derivation,
causing all entries to derive identical keys. `Hkdf::new` is retained.

---

### 5. Vault Header AAD Binding

**Decision**: Every `EncryptedEntry` is sealed with the vault's `header_aad`
(32 random bytes stored plaintext in the vault header) passed as the AAD
field of the AES-256-GCM call.

**Rationale**:
- Without AAD binding, a valid ciphertext from Vault A could be physically
  copied into Vault B's entry list. Decryption would succeed with Vault B's
  key if the entry key happened to be the same (e.g., same password, same
  `entry_id`). This is a *cross-vault entry invasion* attack.
- Binding `header_aad` into the AEAD tag means that decryption of any entry
  from the wrong vault will fail at the authentication step — the Poly1305 tag
  is invalid because the AAD differs. This is verified by the integration test
  `entry_from_different_vault_fails_aad_check`.
- `header_aad` is separate from the KDF salt. The salt is consumed by Argon2id;
  the `header_aad` is bound into every AEAD call. They serve distinct purposes
  and must not be collapsed into a single field.

---

## 6. Vault Serialization: CBOR via `ciborium`

**Decision:** Use **CBOR** (Concise Binary Object Representation) for vault serialization, pivoting away from the initial plan to use **SQLite**.

**Rationale:**
* **Reduced Complexity:** While **SQLite** was originally considered for the database layer, it was determined that the overhead of managing a relational engine, file locking, and migrations made it "overkill" for the benefits for this specific use case. CBOR provides a middle ground—structured data without the weight of a full SQL engine.
* **Binary Security:** As a binary format, there is no risk of accidental string logging of sensitive field names in production logs, a common "leak" with text-based formats.
* **Schema Evolution:** CBOR is highly schema-friendly; it natively supports versioned structs, allowing for future updates to the vault format without breaking backward compatibility.
* **Format Integrity:** Eliminates "foot-guns" common in JSON, such as trailing-comma errors, floating-point ambiguity, or encoding inconsistencies.

---

> **Note:** By choosing `ciborium` as the implementation, memory-safe, high-performance serialization path is confirmed that aligns with the goal of keeping the vault both lightweight and cryptographically secured.

---

### 7. Secret Memory Safety

**Decision**: `ZeroizeOnDrop` on all secret types. Manual `mlock` via `libc`
in `omoide-core` before secret allocation. Core dump suppression via
`setrlimit(RLIMIT_CORE, 0)` + `prctl(PR_SET_DUMPABLE, 0)` at process init.

**Rationale**: Verifies T1.

#### Why `libc` mlock over `memsec`

`memsec` was evaluated as a cross-platform wrapper for memory locking. However, it provides only low-level primitives and lacks a high-level, ergonomic secure buffer abstraction. Other crates providing buffer types were found to be either incompatible with the `argon2` crate's `hash_password_into` API (often requiring intermediate allocations that defeat the purpose of `mlock`) or introduced undesirable dependency weight.

Hand-rolled `mlock` via `libc` was chosen instead:
- `omoide-crypto` remains free of platform I/O dependencies (auditable in
  isolation).
- `mlock`/`munlock` are called in `omoide-core`, which already carries
  platform-level responsibilities (core dump suppression, file I/O).
- Direct use of `libc` provides maximum transparency and control over the
  memory locking process, satisfying T1 without opaque intermediate layers.
- No `unsafe` is introduced into `omoide-crypto` itself.

**Known limitation**: `mlock` is subject to `RLIMIT_MEMLOCK` quota on Linux
(default 64 KiB on most distros). If `mlock` fails, `ZeroizeOnDrop` still
provides post-deallocation zeroing. Failure is logged as a warning, not a
fatal error. Document in release notes.

---

## Consequences

- Vault format version is **v1**. Any change to KDF params, AEAD algorithm,
  or serialization format requires a new version and a migration tool.
- `omoide-crypto` has no I/O or platform dependencies — it is independently
  auditable.
- AES-256-GCM is not effective to use on non-x86-64 machines since they do not contain AES-NI. If
  the target platform ever expands beyond x86-64, reconsider ChaCha20-Poly1305.

## Phase 1: Sample CLI Verification

As part of the conclusion of Phase 1, a sample CLI (`omoide-cli`) was developed to verify the integration of the three core crates (`omoide-format`, `omoide-crypto`, `omoide-core`).

### Crate Integration
The sample CLI successfully utilized the following elements:

1. **`omoide-format`**:
   - Leveraged standard schema definitions (`VaultFile`, `VaultHeader`, `Entry`, `EncryptedEntry`).
   - Verified that vault structures effortlessly serialize to and deserialize from CBOR format (`ciborium`).

2. **`omoide-crypto`**:
   - Used `derive_master_key` and `derive_entry_key` to apply Argon2id and HKDF sequentially.
   - Utilized `encrypt_entry` and `decrypt_entry`, effectively applying AES-256-GCM with AAD binding to secure the CBOR byte payloads.

3. **`omoide-core`**:
   - Implemented `open` and `seal` to read operations and execute atomic file writes to disk.
   - Initialized `suppress_core_dumps` at startup to adhere to memory safety guidelines (T1 threat model mitigation).
   - Since it will be used for hardening, `mlock_secrets` will be used in production build only.

### Results
- The CLI smoothly generates and writes the initial `VaultFile` structure.
- The KDF constraints successfully enforce reliable derivation execution.
- The `header_aad` correctly binds to `decrypt_entry`, validating that cross-vault invasion attacks would structurally fail via Poly1305 authentication rejection.

### Conclusion
The Phase 1 Core Crypto Primitives and Vault Format are functionally complete and robust. The `omoide-cli` serves as a successful proof-of-concept for locking, unlocking, and verifying vault instances safely according to the ADR's specifications. We are now ready to proceed to Phase 2 (Recall Mode engine).
