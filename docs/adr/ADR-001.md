# ADR-001: Vault Format and KDF Design Decisions

**Status**: Accepted  
**Date**: 2026-04-03  
**Project**: omoide — local encrypted secrets vault  
**Author**: Inigo  

---

## Context

`omoide` requires a vault file format and key derivation strategy that satisfies
the following constraints from the threat model:

- **T1** — Secret material must never be paged to swap and must be zeroed after use
- **T2** — Vault file must be resistant to offline GPU brute-force attacks
- **T3** — BIP39 recovery seed wrapping key must be cryptographically independent
  from all vault entry encryption keys
- **T5** — Dependencies must be auditable

The decisions recorded here are **frozen at vault creation time**. Changing KDF
parameters after vault creation requires a migration tool. Do not alter these
defaults without re-running `omoide bench-kdf`, updating this ADR, and
incrementing the vault format version.

---

## Decisions

### 1. AEAD Algorithm: AES-256-GCM

**Decision**: Use AES-256-GCM via the `aes-gcm` RustCrypto crate.

**Rationale**:
- Target platform is x86-64 desktop only. AES-NI is present on all supported
  hardware, making AES-256-GCM faster than ChaCha20-Poly1305 in software.
- Aligns with TLS 1.3 and
  disk encryption ecosystem expectations.
- Nonce-reuse catastrophic failure mode is mitigated by per-entry HKDF subkeys
  (no key is ever reused).

---

### 2. KDF Algorithm: Argon2id

**Decision**: Use Argon2id via the `argon2` RustCrypto crate (`std` feature enabled).

**Rationale**:
- Winner of the Password Hashing Competition (PHC). Memory-hard and
  side-channel resistant (hybrid of Argon2i and Argon2d).
- OWASP-recommended for password storage as of 2024.
- No fallback to PBKDF2 or bcrypt — both are insufficiently memory-hard for
  modern GPU attacks.

---

### 3. KDF Parameters

**Decision**: `m=19456` (19 MiB), `t=2`, `p=1` — OWASP balanced baseline.

#### bench-kdf results

Benchmark run on development machine (Steam Deck, Linux x86-64):

```
omoide bench-kdf — Argon2id parameter survey
Target: ~300ms on this machine

m=19456 t=2 p=1 (default)      =>   37.3ms
m=47104 t=1 p=1                =>   40.7ms
m=12288 t=3 p=1                =>   27.2ms
m=9216  t=4 p=1                =>   23.7ms
m=7168  t=5 p=1                =>   22.0ms
```

Additionally, `benchmark_kdf` will be executed on what was the possible specs for the lowest end machine for development. Kindly refer to the Benchmark environment below:

```
  Host:    Steam Deck (AMD APU, SteamOS)
  VM:      VirtualBox, Ubuntu 22.04 LTS
  vCPUs:   4 cores, 50% execution cap
  RAM:     8192 MB
  Purpose: Approximate low-end x86-64 desktop
```

#### Analysis

All benchmark results are significantly below the 300ms target. This indicates
the Steam Deck (development machine) is substantially faster than a modest
target machine. The OWASP minimum parameters (`m=19456, t=2, p=1`) are
retained because:

1. They represent the OWASP recommended balanced baseline regardless of
   measured latency on this specific machine.
2. The vault will be used on a range of x86-64 hardware — the KDF must be
   acceptable on the weakest plausible machine, not just the dev machine.
3. Changing to higher parameters requires re-benchmarking on the weakest
   target machine and updating this ADR.

#### Why `p=1`

Parallelism is set to 1 (single-threaded unlock path). Rationale:
- `omoide` targets interactive desktop use — a single unlock operation per
  session, not batch processing.
- `p=1` avoids consuming multiple CPU cores during vault unlock, which would
  be noticeable on low-end hardware.
- The memory-hardness guarantee (`m=19456`) provides the primary
  brute-force resistance, not parallelism.

### 4. Subkey Derivation: HKDF-SHA256

**Decision**: Derive per-entry 32-byte encryption keys from `MasterKey` using
HKDF-SHA256 (`hkdf` RustCrypto crate). `MasterKey` never directly encrypts data.

**Rationale** (RFC 5869 compliant):
- `MasterKey` is Argon2id output — uniformly distributed, high entropy,
  qualifies as IKM for HKDF.
- Per-entry HKDF subkeys provide **key separation**: compromising one entry key
  reveals nothing about other entry keys.
- The `entry_id` (UUID bytes, 16 bytes) is used as the HKDF salt, making each
  entry's key unique even under the same master key.
- The `info` tag separates key purposes:

| info tag | Purpose |
|---|---|
| `b"entry-enc"` | Vault entry encryption key |
| `b"seed-wrap"` | BIP39 recovery seed wrapping key (reserved, future sprint) |

**T3 mitigation**: `b"seed-wrap"` and `b"entry-enc"` produce cryptographically
independent keys even if the same `entry_id` is used. This is verified by the
test `entry_enc_and_seed_wrap_tags_produce_different_keys`.

**Why `Hkdf::new` over `Hkdf::from_prk`**: `from_prk` does not accept a salt
parameter — switching to it would silently drop `entry_id` from the derivation,
causing all entries to derive identical keys. `Hkdf::new` is retained.

---

## 5. Vault Serialization: CBOR via `ciborium`

**Decision:** Use **CBOR** (Concise Binary Object Representation) for vault serialization, pivoting away from the initial plan to use **SQLite**.

**Rationale:**
* **Reduced Complexity:** While **SQLite** was originally considered for the database layer, it was determined that the overhead of managing a relational engine, file locking, and migrations made it "overkill" for the benefits for this specific use case. CBOR provides a middle ground—structured data without the weight of a full SQL engine.
* **Binary Security:** As a binary format, there is no risk of accidental string logging of sensitive field names in production logs, a common "leak" with text-based formats.
* **Schema Evolution:** CBOR is highly schema-friendly; it natively supports versioned structs, allowing for future updates to the vault format without breaking backward compatibility.
* **Format Integrity:** Eliminates "foot-guns" common in JSON, such as trailing-comma errors, floating-point ambiguity, or encoding inconsistencies.

---

> **Note:** By choosing `ciborium` as the implementation, memory-safe, high-performance serialization path is confirmed that aligns with the goal of keeping the vault both lightweight and cryptographically secured.

---

### 6. Secret Memory Safety

**Decision**: `ZeroizeOnDrop` on all secret types. Manual `mlock` via `libc`
in `omoide-core` before secret allocation. Core dump suppression via
`setrlimit(RLIMIT_CORE, 0)` + `prctl(PR_SET_DUMPABLE, 0)` at process init.

**Rationale**: Verifies T1. `memsec` crate was evaluated but its `SecBuf`
type is not a correct API. Hand-rolled `mlock` with `libc` was chosen instead,
keeping `omoide-crypto` free of platform I/O dependencies.

**Known limitation**: `mlock` is subject to `RLIMIT_MEMLOCK` quota on Linux
(default 64 KiB on most distros). If `mlock` fails, `ZeroizeOnDrop` still
provides post-deallocation zeroing. Failure is logged as a warning, not a
fatal error. Document in release notes.

---

## Consequences

- Vault format version is **v1**. Any change to KDF params, AEAD algorithm,
  or serialization format requires a new version and a migration tool.
- `omoide-crypto` has no I/O or platform dependencies — it is independently
  auditable.
- AES-256-GCM is not effective to use on non-x86-64 machines since they do not contain AES-NI. If
  the target platform ever expands beyond x86-64, reconsider ChaCha20-Poly1305.
